# Проверенное время и безопасный режим

Расписание, паузы и дополнительные часы работают строго по Москве — UTC+3. Часы и часовой пояс Windows не определяют, можно ли пользоваться компьютером. Выбора другого пояса нет.

## Откуда берётся время

Основной источник — [TimeAPI.io](https://timeapi.io/), запрос UTC по HTTPS. Резервный — серверная отметка `ts` [диагностического ответа Cloudflare](https://developers.cloudflare.com/fundamentals/reference/cdn-cgi-endpoint/) по HTTPS. Ключи и регистрация не нужны. У Cloudflare это диагностический интерфейс, а не специализированный сервис с гарантией точности времени.

Каждый запрос ограничен четырьмя секундами. Старые кешированные ответы, неверный формат и расхождение содержимого с серверным заголовком Date отклоняются. Проверка сертификатов HTTPS не отключается. При очень неверной дате Windows проверка сертификата может не пройти — это приведёт к запрету работы, а не к доверию неправильным часам.

При запуске службы есть до **5 минут** на получение времени и повторные попытки. Пока время неизвестно, родитель может войти и выключить контроль в пульте. Как только время подтверждено, расписание применяется сразу: если сейчас запрещено, остаток пяти минут не предоставляется. Если за пять минут оба источника так и не ответили, при включённом контроле служба начинает выключение. Уведомление родителю может добавить до двух секунд, запуск выключения — ещё несколько секунд.

Эта задержка действует только при отсутствии подтверждённого времени. Она появляется заново после каждого перезапуска службы, поэтому ребёнок также может получить эти минуты, отключая интернет и перезагружая ПК. Это согласованный компромисс для доступа родителя. Для отключения используй переключатель «Контроль включён» в пульте: простую остановку службы может отменить задача-хранитель.

Резервная проверка планировщика перечитывает настройки после ожидания: если родитель выключил контроль, она не выключает компьютер по старому снимку. Лимит её выполнения увеличен до шести минут, чтобы планировщик не оборвал процесс до проверки и выключения.

После успешной проверки время хранится только в памяти: полученное UTC плюс независимый монотонный таймер. Windows [учитывает в этом таймере сон и гибернацию](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps). Сверка с интернетом выполняется каждые 15 минут в фоне. Расписание проверяется с прежним интервалом (по умолчанию 10 секунд). Потеря сети после успешной проверки не сбрасывает часы. Значительное расхождение нового ответа с уже идущими часами не принимается, время назад не переводится.

После перезапуска службы, в том числе после перезагрузки компьютера или сохранения настроек через пульт, нужна новая проверка интернета. Старый файл с датой не используется как доказательство текущего времени.

## Пауза и отключение контроля

- Временная пауза не разрешает работу, если время после запуска не подтверждено.
- Команды `/pause`, `/extra` и аналогичные действия пульта требуют проверенного времени.
- Явное отключение контроля родителем (`/off` или выключатель в пульте) сохраняет прежнее значение: компьютер не выключается по расписанию и из-за отсутствия времени.
- Для проверки свежести команд Telegram используется проверенное время либо серверный заголовок HTTPS-ответа самого Telegram. Это позволяет выполнить `/off`, когда Telegram доступен, а источники времени — нет. Время Telegram не используется для разрешения работы по расписанию.
- Старый `PauseUntil`, содержащий UTC-смещение, автоматически переводится в UTC+3. Новые паузы записываются как московское календарное время без зависимости от пояса Windows. Старое поле `LastTimeZoneId` не влияет на расчёт.

Резервная задача планировщика и пульт сначала запрашивают время из памяти действующей службы через локальный канал. Проверяется PID сервера канала по диспетчеру служб Windows. Поэтому простой процесс с таким же именем канала не может подставить часы. Если канал недоступен, применяется проверка API; отсутствие подтверждения означает запрет. После успешной проверки службы обычная потеря интернета сама по себе не вызывает выключение резервной задачей.

## Что исправлено для безопасного режима

- Установка проверяет значение `Service` в обеих регистрациях SafeBoot — `Minimal` и `Network`; ошибка регистрации больше не скрывается за сообщением об успешной установке.
- Восстановление службы заново регистрирует безопасный режим. Самовосстановление не ждёт планировщик в безопасном режиме и не задерживает основной цикл контроля.
- Результат `shutdown.exe` проверяется. При ошибке или зависании выполняется резервный системный вызов; если оба способа не сработали, ошибка записывается в журнал и следующая проверка повторяет попытку.
- Вспомогательные команды действительно ограничены таймаутом, включая чтение их вывода.
- Необязательный провайдер журнала событий не подключается в безопасном режиме. Ошибки старта дополнительно записываются в `%ProgramData%\KidsLocker\service.log`.

Эти исправления закрывают обнаруженные дефекты кода, но не доказывают причину прежнего инцидента без журналов целевого ПК. Автоматические тесты не перезагружают Windows в безопасный режим и не проверяют физическое выключение. При административных правах у ребёнка остаются способы отключить саму защиту; API времени этого не отменяет.

## Сбор диагностики на целевом ПК

Новый exe поддерживает `--diagnose <путь-к-отчёту>`. Команда только читает состояние службы, её параметры, записи SafeBoot и последние относящиеся к KidsLocker события. Конфигурация с токеном и паролем в отчёт не включается. Служба не устанавливается, компьютер не выключается, запросов в сеть нет.

Пример в PowerShell из папки со скачанным exe:

```powershell
$report = Join-Path $env:USERPROFILE 'Desktop\KidsLocker-diagnostics.txt'
Start-Process -FilePath '.\KidsLocker.exe' -ArgumentList @('--diagnose', ('"' + $report + '"')) -Wait -WindowStyle Hidden
```

Отчёт полезно собрать после воспроизведения сбоя. Регистрация в реестре подтверждает настройку запуска, но сама по себе не подтверждает, что процесс действительно запускался и успешно выключал ПК.

## Выпуск и установка обновления

Существующий процесс выпуска не меняется: GitHub Actions по тегу `vX.Y.Z` запускает тесты и публикует один самодостаточный `KidsLocker.exe` вместе с SHA-256. Для обновления службы нужно скачать новый exe, открыть пульт и повторно установить службу в нужном режиме. Замена только скачанного файла вне каталога установленной службы её не обновляет. Перед боевой установкой проверьте сеть, московское расписание и режим службы.
